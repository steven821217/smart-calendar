## 二、優化項目（依貢獻排序）

### 1. 子句因子化：把複合需求拆成可獨立處理的子句

**問題**：「明天有什麼會，然後下週一有沒有空」這類複合需求，單次理解會漏掉後半。

**做法**：先由一個受限的 Planner 拆子句，每個子句**用同一個分類器重新判斷**意圖（不信任 Planner 的側標籤），全體先做 preflight，再並行執行 specialist，最後由 Composer 合併。

**效果**：119/124 → **124/124**。

**文獻依據**：arXiv:2603.28929 ClauseCompose（連接詞轉換下 EM 由 10.4 → 86.7）；ACL 2023 Industry Track 的語意解析模組化。

來源：`v1-baseline` → `v2-clause-factorized`

---

### 2. 確定性 cascade：能不用模型就不用

**問題**：簡單查詢也要付 2–4 秒的模型延遲。

**做法**：tier-0 用確定性覆蓋檢查，通過就完全不呼叫模型。

**效果**：28 題走此路徑，median **14 ms**（vs 經模型 3,807 ms，約 **270 倍**差距）。整體 median 由 6,130 ms（v12）降至 3,755 ms（v25），降幅 **39%**。

**文獻依據**：ICLR 2025《Faster Cascades via Speculative Decoding》的 deferral rule 與品質中立性；arXiv:2509.21837 agreement-based deferral（成本降至 40%、延遲最多降 60%）。

來源：`v12-bank-expanded` → `v13-cascade` → `v25`

---

### 3. 推測式執行：檢索一致時就先跑

**做法**：ICL 示例檢索的前兩名 family 一致時，與 family 分類呼叫**並行**預跑 specialist，等於藏住一次模型往返。

**效果**：品質不變（313/313），省下一次 ~2.4 秒的序列等待。可由 `INAPP_SPECULATE` 開關。

來源：`v17-speculative`

---

### 4. 精簡第一層 schema

**做法**：第一層 family 分類的輸出移除 `evidence_spans` 欄位。

**效果**：每次結構化輸出由 73 → 60 tokens。以實測 29–30 tok/s 計，**每題省約 0.5 秒**。

**量測依據**：生成吞吐 29–30 tok/s（150 秒持續負載無降頻，clocks 穩定 2797 MHz）；每次結構化輸出約 70 tokens ≈ 2.4 秒。

---

### 5. 兩 agent 真協作（本輪重點）

**問題診斷**：原本兩種模式都不是協作。用紀錄證實——39 次工具呼叫**全部**是 `plan` 模式、10–56 ms，本地 14B 一次都沒被呼叫，GPU 全程 0%。

| 模式 | 誰做理解 | 誰做推理 | 本地模型參與 |
|---|---|---|---|
| `question` | 本地 14B | 本地 | 是（外部只是轉傳，浪費外部能力） |
| `plan{}` | 外部 | 外部 | **否**（本地退化成帶 RLS 的資料庫） |
| **`detail="auto"`** | **本地先自評** | **依能力分工** | **是** |

**做法**：本地先做**確定性**能力自評，能答就自己答（省外部 token、資料不出本機）；遇到本地工具面沒有的運算，回 `kind="escalate"` 並附上**已換算本地時區的事實**，外部一次完成推理，不需第二次往返。

八類會觸發升級的運算子：極值、聚合、衝突偵測、分組比較、跨實體列舉、衍生間隔、相依查詢、無界列舉。

**關鍵設計決定**：能力缺口類**不先跑模型**。本地再有信心也算不出「總共幾小時」，先跑一次只是白付 2–4 秒。

**效果**：3/12 → **11/12**。GPU 實測取樣到 63–98% 使用率、峰值 98%（先前 plan 模式全程 0%）。

**文獻依據**：SWARM-LLM（IEEE VTC2026-Spring，Dahshan et al.，程式碼 github.com/mdahshan/swarm_llm）的門檻式升級——其實測 edge-only 困難題 0.00 → 選擇性升級 0.15，雲端曝露率降 **72%**、token 曝露率降 **58.7%**；Hybrid LLM（ICLR 2024）、FrugalGPT（TMLR 2024）的成本／品質路由。

**刻意的偏離**：不採用 SWARM-LLM 的自評信心訊號。arXiv:2504.04718 與 EMNLP 2025《Too Consistent to Detect》都指出小模型自評不可靠，因此改用兩類可驗證訊號：(a) 能力缺口（確定性運算子偵測）(b) 執行過程被標記 uncertain 的推測步驟。

來源：`apps/api/src/mcp/collaboration.ts`、`escalation-facts.ts`、`eval/EXTERNAL-SUMMARY.md`

### 6. MCP 介面工程：對抗工具空間干擾

**問題**：外部 agent 可用的工具一多、回應一長，表現就崩。

**做法**：
- 回應分層 `brief` / `structured` / `evidence` / `auto`，呼叫端自選細節量
- 分頁（page_size ≤ 50）、自然語言訊息上限 2000 字
- 工具命名空間正名（`calendar_*`），舊名保留為 deprecated 別名
- Server card 宣告實測延遲、可用意圖、每個意圖回什麼、隱私邊界、升級政策

**文獻依據**：Microsoft Research 2025-09《Tool-space interference in the MCP era》——調查 1,470 個 server，工具過多使表現降 **85%**、回應過長降 **91%**，建議 server card／命名空間／階層式工具集；Anthropic 2025《Code execution with MCP》的 progressive disclosure（150k → 2k tokens）。

## 三、量測到的硬體邊界（決定所有延遲設計）

| 項目 | 實測 |
|---|---|
| 生成吞吐 | 29–30 tok/s（150 秒持續無降頻） |
| prompt 處理 | 1,433 tok/s 冷啟；23,899 tok/s（prefix cache 命中） |
| 每次結構化輸出 | ~70 tokens ≈ 2.4 秒 |
| flash attention + q8_0 KV cache | 速度僅 +2%，但省 **2.6 GB** VRAM |
| 並行吞吐 | 1 req 2.77s；2 req 3.87s（聚合 1.46×）；3 req 5.12s（1.62×） |
| 本地跑 120B 模型 | **不可行**——需約 61 GB，本機上限約 46 GB |

**設計推論**：14B 每次結構化輸出固定成本約 2.4 秒，所以優化方向只有三條——減少呼叫次數（cascade）、縮短輸出（精簡 schema）、藏住往返（推測式執行）。三條都做了。

## 五、方法論：這套評測本身的設計

能講的重點在於**如何讓數字可信**。

1. **GPU preflight**：每輪評測啟動時查 Ollama，任何模型 `size_vram/size < 90%` 就**中止整輪**，裝置狀態寫進結果檔。起因是實際發生過兩次 CPU fallback（CUDA error 800），導致延遲數字全部無效。
2. **題號一經發布不可更改、既有題目措辭不可修改**，新措辭只能新增題目——確保跨版本可比較。
3. **期望值只依賴 seed 固定資料**，用相對日期；資料量綁定的期望值必須寫成函式。
4. **禁止受測 agent 看期望值**：明列禁讀題庫、紀錄、結果檔，禁止直連資料庫。
5. **靜默失敗要能被抓到**：紀錄的題號對不上題庫時明確警告，全部對不上直接拋錯（實測發生過——題號被寫成 `01` 而非 `EX01`，計分回 0/0 卻沒報錯）。
6. **誠實修正期望值並留記錄**：兩題原期望值太寬鬆或太窄，修正後外部 agent 成績由 11/12 降為 10/12。修正記錄留在題庫註解。
7. **版本 × 題目矩陣**：25 個版本的逐題結果都留著，任何優化都能立刻看出是否造成回歸（例如 `v6-planner-first` 曾讓 MU07 回歸，`v18-lean-family` 讓 DF04 回歸，都是這樣抓到的）。

## 六、一個反直覺但重要的觀察

協作模式下，這批推理題的**本地 GPU 呼叫次數反而更少**——因為正確的分工就是「本地算不出來時不要硬跑」。

GPU 使用率不是目標，正確分工才是。在 313 題日常題庫上本地仍承擔幾乎全部工作，其中 28 題連模型都不必啟動。

## 七、建議的簡報敘事線

1. 目標：隱私敏感的日曆助理，資料盡量不出本機，但又要能回答困難問題
2. 硬體現實：14B 每次結構化輸出固定 2.4 秒，120B 跑不動 → 這是所有設計的起點
3. 本地路徑優化三招：減少呼叫（cascade 14ms）、縮短輸出（省 0.5s）、藏住往返（推測式）→ 313/313，median 由 6.1s 降到 3.8s
4. 但 14B 在推理題只有 3/12 → 需要外部強模型
5. 拆穿假協作：用紀錄證明 GPU 全程 0%，本地只是資料庫
6. 真協作：確定性能力自評 + 升級時附證據 → 11/12，GPU 峰值 98%
7. 誠實邊界：協作讓本地做得更少但整體更對；負面結果四項；評測方法論如何防自欺
